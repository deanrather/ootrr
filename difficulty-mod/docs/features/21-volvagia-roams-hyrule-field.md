# Volvagia roams Hyrule Field

Setting `volvagia_roams` (number 143, default off). Branch `feature/volvagia-field2` in `worktree volvagia`.
**Built in the files (Route A, custom actor), not yet run in the game.** Test plan: `<playtest folder>\volvagia\PLAN.md`.
(The first attempt, `volvagia_field` on `feature/volvagia-field`, built nothing; its findings are kept below under "First investigation".)

## Request
"let volvagia roam above hyrule field as an adult." On the earlier "not possible" verdict (20 Nov): "yes, try a few things. What's the limitation here? Can't we just make our own logic if we need to?"

## Interpretation
In adult Hyrule Field a Volvagia flies about and attacks. It must not block anything, must not make a seed unbeatable, must not crash the field and must have no story effect. Killing it gives nothing.

## How it works (Route A: our own actor class)
**Vanilla precedent.** The game already clones Volvagia once: `Dm_Enemy_DungeonBoss_Volvagia` is the Volvagia pack plus one ActorParam whose `$parent` is `Work/Actor/Enemy_DungeonBoss_Volvagia...ActorParam.gyml` and which overrides one reference (its model). Its ActorInfo row is a copy of Volvagia's with `ActorName`, model, ELink/SLink user names still `Enemy_DungeonBoss_Volvagia`. The randomizer's `cow_clone` module registers new actor classes the same way (new pack, ActorInfo, GameActorInfo and Tag rows, size table entries). We follow both.

**The clone `Enemy_Volvagia_Roam`** (`difficulty/volvagia.rs`): new pack = the whole Volvagia pack (211 files, unchanged) + four files of its own:
- ActorParam: `$parent` Volvagia's; overrides `GameParameterTableRef` (own table), `DeathRef` (see below) and `BattlePresentationRef` → `EnemyCommon` (normal enemy battle music `BGM_EnemyBattle` instead of `EnemyDungeonBoss`, which carries `BGM_DungeonBoss` and the boss presentation class).
- GameParameterTable: Volvagia's, with `DungeonBossCommonParam` and `DungeonBossVolvagiaParam` pointed at own copies.
- DungeonBossCommonParam: no `Appear` entry; `Die` kept with an empty event name and the start condition the game uses for Appear. Why this is safe: `BossCommon.StartEvent.module` switches on the condition: case 0 never, case 1 "AI condition met" (an input), case 2 "is dead". Volvagia's brain calls it for `Die` with that input fixed to false. Die's own value must be "is dead"; Appear's (a different valid value) is case 0 or 1, so the Die request can never fire, and even if it did it names no event. Nothing in the actor's graphs asks for "Appear"; the vanilla intro is started by the boss room.
- DungeonBossVolvagiaParam: Volvagia's, the seven circle/leave distances times the scale switch (default 1).
- Rows in `RSDB/ActorInfo` (heap grown by the pack growth), `RSDB/GameActorInfo`, `RSDB/Tag` copied from Volvagia's; size table entries for the pack and the four files (learned from their Volvagia peers, as cow clones do). Done in its own step after the late files and cow clones (`slice/edit.rs`), because the generic late path cannot size a pack that does not exist in the game.

**Placement.** The 8 holes (`Zero`..`Eight`, there is no `Four`) and `RoomCenter` are read at build time from the dream world Volvagia stage (same layout as the Fire Temple room: a test checks this) and placed around the arena point with the same links, plus the actor, in one far-delete and one simultaneous group. No `IsIntendedForEventAppear`, no room logic, no lava plane link, no falling rock manager, no heart container. Holes are 5 to 14 units from the centre; the AI's circle moves use the room centre and the distances in its own parameters.

**Two stages** (env var `OOTRR_VOLVAGIA_STAGE`): `1` = ruined Market plaza `Market_Adult` (-1.9, 100.07, 12.4), a throwaway test map (the Market was wrong for players: ReDeads, already deadly; kept for testing only); otherwise (the default) adult Hyrule Field `HyruleField_Adult` only, at (-36.0, 148.2, 120.0), the flat central plain. Chosen from the adult field navmesh: ground within 8 units of that height in all 16 directions out to 60 units (her circles are 25 units and she leaves up to 30 from the centre), wall clearance 12+, and at least 60 units from every exit, arrival point, the Market gate (76 away), the Lon Lon Ranch gate, the Iron Knuckle (134, 168.5; 177 away), the three fireball storm spots (114, 115, 143 away), the Gerudo gate and the Dead Hand hole. The Market-to-ranch road passes close by, so she is met by players who cross the field. Her wake distance (about 18 seen) is inside her brain graph, not a parameter, so it is unchanged. `OOTRR_VOLVAGIA_LIFT` (0 to 60) raises the whole ring; `OOTRR_VOLVAGIA_SCALE` (0.5 to 4) spreads holes and circle distances.

**"Attacks".** It keeps all of Volvagia's AI: jump out of a hole, fly arcs and circle the centre, fire breath (with its fire field), air dive, dive back into a hole, chance time on the ground. Falling rocks need the room's rock manager, which is not placed, so that attack should do nothing.

**Corpse and scaling fixes (20 Nov, after the first field playtest, not yet replayed).**
- Corpse: in the playtest her neck and belly stayed standing and burning at the hole until the map reloaded. Cause: Volvagia's own death table (`System/CombinationDataTableData/DungeonBossVolvagia_..._DeathReasonProcedures`) sets `LifeDepleted` to `IsRequestDestruction` false, so the actor is never asked to delete itself; in the Fire Temple the room logic removes it. The clone's ActorParam now points `DeathRef` at the pack's own `Component/DeathParam/DungeonBossCommon` file, whose table (`DungeonBossCommon_...`) only clears the effect names and leaves the ordinary enemy default (destroy after the death). No event name, no Sage or BossIn text, no flag writes beyond the ordinary enemy respawn bit are in that data (a test checks). Not touched: the real Volvagia's death table.
- Scaling: the difficulty module edits the life, attack, movement and pace files of every existing enemy pack, but the clone pack is built afterwards from the game's pack, so it skipped that. It is now built from the already staged (scaled) Volvagia pack when there is one, so `enemy_health`, `enemy_damage` and `enemy_speed` apply to it the same way (hp 60 becomes 30 at 50 %). Test: stage with health 50 and damage 200, the clone's `MaxLife` is 30 and its attack file differs from the plain one.
- Open risk: Volvagia's AI death action (`interruptdie`) may itself wait for the Die event; the Die event has an empty name, so it should pass. If the corpse still stays, the next step is cutting that action.

**Reappears until the real Volvagia is beaten (20 Nov, user: "make her keep reappearing in the field till she's defeated in fire temple. Then she can stop respawning there"; not yet run).**
- Respawn: the game writes a defeated enemy down in two flags of the "life ran out" cell of its death table, `IsSetRespawnFlagToFalse` (the area flag) and `IsSetGmdRespawnFlagToFalse` (the saved one); the ordinary enemy table sets the first, and `enemies_respawn_sooner` (feature 14) shows that setting both false means a kill is never recorded. The clone now has its own death table, a new loose file `System/CombinationDataTableData/Enemy_Volvagia_Roam_game__death__DeathReasonProcedures...bgyml` (since 21 Nov a copy of Volvagia's own `DungeonBossVolvagia` table, see below), and its own DeathParam file in the pack (since 21 Nov a copy of Volvagia's own, pointing at that table). Volvagia's own death file in the pack and the shared tables are untouched, so the real Volvagia and other bosses are as before. Only the life-ran-out cell is changed: a kill by other reasons (crushed, drowned, burned away) is still written down.
- Gate: the actor in the field map carries a `Presence` of `HavePlayedEvent.Dm_FireTemple_BossOut` with `IsNegation` true, so the map creates her only while that flag is not set. The flag is the one the Fire Temple victory scene sets when it plays right after the real Volvagia dies. Not used: `IsGet.Item_Medal_Fire` (a randomized seed can hold the medallion elsewhere, so it can be set before the fight), `SageOfFire_IsAfter_DefeatBoss_Exp` (true only at one step of the sage quest), `HaveDefeatedEnemy_Enemy_DungeonBoss_Volvagia` (the field clone keeps Volvagia's enemy parameters and may count toward it, which would end her respawn after the first field kill). Stateless: it reads a flag the game saves and adds none. The holes are plain anchors and stay.
- Unknown until run: whether the flag is set when the victory scene is skipped with `skip_cutscenes`; whether the map really skips a `Presence` actor for the negated check; whether the kill leaves her away on reload (the Gmd flag set elsewhere, for instance by the enemy dictionary).
- Tests: the clone pack has five own files and the death file points at the own table; the table's life-ran-out cell has both flags false and still has empty effect names; the death files carry no event, Sage or flag text; the field actor has the negated `Presence` and the anchors have none; the flag is in `data/flags.json` as an ordinary saved flag; the new loose file gets a size table entry.

**Two regressions found and fixed (21 Nov).** The corpse fix (`6c4ff37`) stopped the hammer hurting her, and the respawn gate (`d7d7c22`) stopped her appearing at all.
- Hammer: `6c4ff37` changed two things, the scaled pack and `DeathRef`. A file-by-file diff of the staged pack against the game's shows that scaling changes only `Life/LifeParameters/...Volvagia` (`MaxLife` 60 to 30) and no damage, guard, weak point or reaction file. The other change replaced Volvagia's own death table with the plain boss one, whose parent is the ordinary enemy table. That throws away her own death rules: the `AI` death reason with her death procedure, and the ignored reasons (`Burned`, `Exploded`, `LifeCondition`, `PhysicsKinematicCollision`, `Eaten`, `PickedUp` and more; the ordinary table counts `ChemicalCriticalHitFire`, `Drowned` and `Crushed` as deaths). Fix: her DeathParam is again a copy of Volvagia's own (same parent), pointing at a copy of Volvagia's own table, `DungeonBossVolvagia_...`, with only three values in the life-ran-out cell changed: `IsRequestDestruction` true (the corpse fix) and the two respawn flags false. Every other cell is the game's, byte for byte (a test checks).
- Absence: the `Presence` was not the cause. It has exactly the form of the game's own 43 "present while a `HavePlayedEvent` is not set" entries (`FlagName`, `IsCheckLazy` false, `IsNegation` true, in that order; a test compares it with vanilla maps). A build without the `Presence` was also empty in the game. The cause was the size table: a loose death table needs its file length plus 5.3 to 9 KB in the resource size table (Volvagia's: 1,776 bytes, entry 9,792), but the new file got its length plus 1 KB, so the game could not load the table, and an actor whose death parameters fail to load is not created. Fix: the new table's size is learned from its two peer tables, the same way the pack's own files are sized (a test pins it at no less than Volvagia's entry).
- Seen in the game (21 Nov, scripted, `<playtest folder>\volvagia\RESULTS-fix.md`, "Fix 4"): she appears on a new save (hp 30/30 at `enemy_health` 50), the Megaton Hammer at her hole took her 30 to 0 in about 7 minutes, the death burst played with no event and no body was left, she was back after Kakariko and back, and with `HavePlayedEvent.Dm_FireTemple_BossOut` set by the bridge she was not created (nothing woke or burned Link at her start for 30 s; flag cleared, she was back). Not tested: whether the real victory scene sets that flag with `skip_cutscenes`, the real Fire Temple fight with the hammer, `enemy_damage`.
- Tests added: the staged Volvagia pack changes no damage, guard, reaction or death file and the clone keeps every staged file byte for byte; the clone's death table equals Volvagia's in every cell but the three values; the gate has the same keys, order and types as the game's own negated gates (three vanilla maps); the new table's size entry is at least Volvagia's.

## Death and purple rupee (branch `feature/volvagia-fix`, 22 Nov)

**Request.** (21 Nov, hands-on) When she is beaten in the field she froze just before her death animation. The user asked for a red rupee when she dies, then for her to flee. Decision (22 Nov): keep her deadly and on the road, damage follows `enemy_damage`; the rupee comes from her own drop table.

**The freeze.** Volvagia's own death table, in the cell for a life that ran out, says `IsWaitForSignal` true: the real fight waits for the Fire Temple room logic to send the death scene signal, and the field has no room logic, so the clone most likely waited for a signal that never comes (the field kill stopped freezing once the value was cleared, seen in the game on the earlier branch). The clone's own copy of the table (the one that already sets `IsRequestDestruction`) now also sets `IsWaitForSignal` false. A build refuses to continue if the game's table does not hold the value it expects. The real Volvagia's table is untouched.

**The purple rupee (50).** User decision, 22 Nov: she drops 50 rupees, not 20, so the item is `Obj_Rupee_Purple`. The first version of this branch dropped a red rupee (20). The clone gets a drop component of its own, shaped like the ones the game gives ordinary enemies:
- Two files copied unchanged from the Floormaster pack, both ordinary shipped files with their own size table entries: the `Drop` blackboard table (declares the drop actor parameter) and the `Default` drop parameters.
- Three files of her own: a `DropParam` (copy of the game's plain `Drop_Default`) whose table list names her own drop table; her `DropTable` (copy of the game's empty `DropTable_None`) whose sub table list names her own sub table; her `DropSubTable` (copy of the empty one) with one item: `Obj_Rupee_Purple`, type `Rupee` (the one generic type all shipped rupee drops use, 995674644), one piece, 100 %, replacing the global drop lottery (`IsReplace`).
- Her ActorParam gets one more reference, `DropRef`, to her own `DropParam`. Nothing else of her actor changes.
- Size table: each of her new files gets an entry of at least its parent file's entry plus its own length (a clone whose entry does not cover its parent chain is silently never created; the earlier tries at a drop that "stopped her loading" may have hit this, which is not proven).
- Purple rupee check in the game files: `Obj_Rupee_Purple` ships as a pack with its ActorParam, and the randomizer already places it as an item, but no shipped drop table names it; the shipped drops use the Green, Blue, Red and Gold rupee actors (Gold: Skull Kid) with the same `Rupee` type, so the drop is chosen by actor name and purple should work the same way. It is the first time purple is a drop, so the game test must confirm it (a test checks the pack, its ActorParam and that Skull Kid's gold drop has the same type). No size table change was needed.
- The route was chosen from the round 5 game test (22 Nov, 13 variants, one scripted run each): copying the plain drop files with a map-entry drop (v7, v8) or a Skull Kid copy (v11, v12) were tried beside it and her body did not go away in those runs; her own table (v9) and the same with a reserve node (v10) both gave a clean death (gone within 12 s, frames running) and 20 rupees in the wallet after Link walked over the spot (red rupee, before the change to purple), so the shorter one (v9) is kept, with no AI graph edit and no map change. One run per variant is thin evidence: the hand test below matters.

**Not changed: regen.** Enemy regen (feature 09) does not heal her, and this branch does not try to. What the files show: her pack's utility graph runs the same damage colour module as other enemies, so the regen nodes are hosted in her copy of the graph (a test on the earlier branch showed it), and the game's own Floormaster does heal from the same nodes. Thirteen builds in the game (hosted nodes moved into her brain graph, the Navi hint removed from her utility graph, the heal scaled to a twentieth of her life, her own life and heal files without the boss heal extension, no hit or alive gating) never moved her life up even once in 75 s after `enemyhp` set it to half. Her utility graph has no Enter/Update/Leave root and holds a Navi hint one-shot beside the damage colour call, which suggested the timers were restarted every frame, but removing the hint did not help either. Nothing in her graphs, her life files or her death table explains it; the one boss-specific rule found is the "guts" flag (`DungeonBossCommon_IsEnableGuts` in her heal parameters, set by her utility graph when her life is 1), which is a survive-at-1-hp rule, not a heal gate, and is why a script kill leaves her at 1 hp until a real hit lands. Finding the cause needs her life component read in a running game, so it is dropped: she does not heal, and the setting's tip says so. The real Fire Temple Volvagia has the same behaviour as before.

## Crash on loading adult Hyrule Field (23 Nov): the death table's size entry

**Symptom.** The build with the seven drop cells (h15a6) crashed 4 of 4 times as adult Hyrule Field loaded: an access violation writing guest address `0x50` in the `GeneralFormatAsync_` thread, right after the clone's death table was loaded. The build before it (h15a4) loaded. Only two files differed: the death table (1816 to 2416 bytes, 12 to 17 cells) and the size table.

**What the files show.** The new table's structure is the game's own: keys and strings sorted, every cell typed `game__death__DeathReasonProceduresCell`, only field names and value kinds the game's tables use. Partial cells are normal (`EnemyCommon` has cells with only `$type` and one value, and `DungeonBossCommon` has nothing else). So the form was not the problem. The size entry was: across all 203 death tables in the game, the entry is close to `file length + about 5,100 to 5,400 + 240 bytes per cell` (for example `DungeonBossVolvagia` 1776 bytes, 12 cells, entry 9792; `EnemyCommon` 1684, 17 cells, 10896; `Default` 2128, 16 cells, 11104). The loaded table costs 240 bytes per cell, not just its file length. The old sizing took the largest overhead of the peers (8016) plus the new length plus 1 KB: 11456 for a table that needs about 11,650. The five added cells cost about 1,200 bytes, more than the 1 KB margin, so the resource heap was too small; a null allocation written at offset 0x50 fits that. h15a4's table (12 cells) had an entry of 10880 against about 9,820 needed, which is why it loaded.

**Fix.** The death table's entry is now the game's entry for `DungeonBossVolvagia` plus the aligned growth in length, plus 256 bytes per added cell, plus 1 KB: 12736 for the 17-cell table. A test checks the per-cell rule against every death table in the game (the 240-byte cost and a 5,040 to 5,400 base hold for all of them, and the rule from Volvagia's entry covers each one) and that the entry is at least 512 bytes over what the rule needs. Another test round-trips the new table byte for byte and checks every cell field against the names and value kinds the game's tables use.

**Tests.** `cargo test -p ootrr-core volvagia` 15 pass and `difficulty` 309 pass (1 ignored) with the game files. Not run in the game yet.

**Note for the next feature.** A loose table's entry does not scale with its file length alone. Before growing any table-like file, fit its kind's entries against a count (cells, rows, entries) over all the game's files of that kind. The respawn feature also adds a `LifeDepleted` cell to tables that lack one (one cell, 240 bytes, inside the 1 KB margin the late stage adds); any edit that adds more than about four cells to one table needs this rule.

**Bisect pair** (in `<playtest folder>\volvagia-drop\mods\`): `h15a7v` is the fix. `h15a7v-small` is identical except that the death table's size entry is set back to 11456 (h15a6's). If `h15a7v` loads and `h15a7v-small` crashes, the size entry is proven to be the cause.

## Hammer kill drops nothing (23 Nov, h15a7v): the drop moves into her die graph

**Result that led here** (scripted, one game copy, mod h15a7v). The field loads (the size fix above is proven by the bisect pair), she does not heal, there is no freeze and she is back after re-entering the field. But two real Megaton Hammer kills (life 20 to 0 in about 3 s, her `Die` animation playing) left no rupee within 150 to 300 units for 25 s and the wallet did not change, although every enabled death cell has `IsDropItem` true and `IsWaitForSignal` false. The bridge `kill`, `damage` and `enemyhp` cannot take her below 20 life in this build (a floor in her boss phases), so the earlier "a bridge kill drops 20 rupees" result came from another code path and is no control any more. Conclusion: her hammer death does not reach the native death-procedure drop, whatever its death reason.

**What ordinary enemies do that she does not** (read in the files). Enemies that die in the air or out of the ground set a forced drop spot before they die: `OneShotDropSetForceDropPos` with `IsForceAllPostureType` true (Keese, Guay, Stalchild, Beamos, `EnemyCommon.common.ragdolldie`, and the shared `SetupForceDropPos.module`, which takes the actor position or the `Body_Root` bone plus (0, 4, 0)). The property's name says a drop is otherwise skipped for some postures; she is a flier that dies with her head out of the ground. Like Like and Big Poe also call `OneShotDropReserveDropItemCreate` in their die graphs (Like Like every frame for five frames before the shared death module, Big Poe once on Enter); the Poe lanterns reserve and then request their own death with `IsWaitForSignal` false, the same setting her table now has. Her die module (`Enemy_DungeonBoss_Volvagia.action.interruptdie.module`, 24 elements, top node a parallel) has neither node. The tester saw her `Die` animation on the hammer kill, so that module runs on the real kill.

**Change (option B, the default).** New file `difficulty/volvagia_die.rs`. In the clone pack's copy of her die module, five nodes are added and the last two are plugged at the end of the top parallel: her position (`QueryActorGetPostionAndRotation`, `QueryMathMtx34fToVec3fMat33f`, `QueryMathAddVector3f` with (0, 1.5, 0), the chain the enemy backup feature already uses in the game), `OneShotDropSetForceDropPos` (`ExecuteEveryFrame` false, `IsForceAllPostureType` true, `Pos` from that chain), then `OneShotDropReserveDropItemCreate` (`ExecuteEveryFrame` false, as Big Poe). No `ExecuteDeathSignalDeathProcedure`: nothing waits for a signal, and leaving it out means that even if the edited module were ever used by the real Volvagia it could not end her Fire Temple death early (the real Volvagia has no drop parameter, so the reserve does nothing there). Her death table cells stay as above (`IsWaitForSignal` false). The drop table is still ten blue rupees.

**Fallback (option C, test switch only).** `OOTRR_VOLVAGIA_DROP=pay` at build time puts one `OneshotIncreaseRupee` 50 in the same parallel instead (wallet only, no rupee on the ground; the node and its form are the ones round 5's `pay` variant used, which paid 20 at once in the game). Any other value or none builds option B.

**Size.** The die module grows from 8,701 bytes; it shares its path with the real Volvagia's file, so its size table entry is grown by the aligned growth plus the usual 1 KB margin (`Made.grown`, applied in `sized`, as round 14 did). Growing the shared entry only gives the real Volvagia's file more room. The pack's heap already scales with the pack.

**Tests** (`cargo test -p ootrr-core volvagia`, game files): the switch reads `pay` only; the drop edit adds exactly the five nodes in that order, keeps every original element and plug, plugs the force and reserve nodes last into the top parallel, reads the position chain, passes the audit and reads back byte for byte, and a second edit is refused; the pay edit adds one node with `Value` 50; the force node has the properties and inputs of the one in `SetupForceDropPos.module` and the reserve node those of Like Like's; staging in both modes grows only the die module and its size entry by at least the growth; every other file of the clone pack is still the staged Volvagia file byte for byte.
